PsychDeep 1.2

Updated // 2026-08-26 Status // active development prototype Domain // digital mental health Source // master branch

PsychDeep 1.2 is a research and development prototype for longitudinal self-report, professional follow-up and risk monitoring in stimulant-use and chemsex contexts. Its central design decision is that language models may converse, extract structured signals and assist a clinician, but they do not decide the risk level. The final 0–4 level comes from an explicit deterministic rule engine whose inputs and calculation trace remain inspectable.

What is implemented now

The current master branch is substantially different from the early PsychApp prototypes documented in June and July. It contains a patient-facing application, professional views for therapists and supervisors, clinical-administration functions, longitudinal check-ins, diary and chat data, a safety plan, a grounding/urge-surfing interface, audit trails and a deterministic risk pipeline.

  • 17 deterministic risk rules. Each assessment persists the selected rule, the evidence used and an immutable calculation trace rather than asking an LLM to produce a clinical severity label.
  • Three LLM roles. A conversational agent, one merged structured analyser for linguistic and psychosocial information, and a read-only clinical copilot for the therapist.
  • Patient-specific baselines. Linguistic scores can be interpreted both against absolute thresholds and against the person's own history. The relative signal supplements rather than replaces absolute safety thresholds.
  • Facts remain separate from inferences. Explicit declarations and clinician-confirmed information are stored separately from model-derived signals.
  • Clinician correction is first-class. A therapist can refute a model inference; the signal stops contributing to subsequent calculations while the original row, source text and correction remain available for audit.

The August reconfiguration

A six-phase sequence merged into master on 25 August 2026. The work was driven partly by a concrete false positive: future-oriented language about changing life for the better was interpreted as a possible farewell. Instead of simply lowering sensitivity, the implementation changed the information architecture around the model.

  • LLM endpoint control was hardened. Runtime redirection is disabled by default in the hosted blueprint and write controls are restricted to clinical administrators.
  • Model configuration became role-specific. Conversation, analysis and clinical copilot can record and use their own model settings while sharing one active endpoint configuration.
  • Two duplicate text-analysis calls became one. Linguistic and psychosocial extraction now share a structured analyser, reducing provider calls while preserving both output contracts and their traceability.
  • The analyser now knows the patient's baseline and accumulated profile. It can distinguish a globally high score from a value that is unusual for that specific person.
  • False-positive control became explicit. Change talk, future plans and context-sensitive leave-taking are handled more carefully, and a clinician can directly refute a linguistic inference.
  • The conversational agent gained continuity without receiving raw engine internals. It can use confirmed facts, the safety plan, recent check-ins, a clinician-editable portrait and a small agenda of open threads. That agenda is dropped entirely in higher-risk crisis states.

Why the engine remains deterministic

The LLM layer is useful for language interpretation and interface behaviour, but those are precisely the components most sensitive to model choice, prompt wording and provider behaviour. PsychDeep therefore stores model provenance and keeps the final alert cascade in ordinary application code.

This does not make the system clinically validated. A deterministic rule can still be poorly designed, a model can still miss or invent a linguistic signal, and thresholds can still be wrong for a real population. The gain is narrower: the path from input to alert can be reproduced, inspected, challenged and tested.

False positives, human review and auditability

PsychDeep treats a model inference as something that can be wrong. Refuting it does not delete history: the original signal stays attached to its source, a corrective fact records why it no longer counts and the engine is re-evaluated from the remaining active evidence. That keeps both the machine's original reading and the human correction visible.

The same principle applies to patient profiles. The therapist can edit the accumulated portrait, open conversational threads and the interpretation of a personal baseline. Those edits guide future dialogue but are not silently converted into risk evidence.

Deployment and data boundary

The repository contains a Render blueprint for a FastAPI API and a static React/Vite frontend, backed by PostgreSQL on Supabase. The hosted configuration names psychdeep.bfab.io as a production frontend origin, disables demo-data seeding and keeps runtime LLM endpoint override off by default.

The database deployment is reproducible from an empty project through ordered migrations and a verification script. Sensitive tables are designed around a dedicated backend role with forced row-level security and no direct PostgREST access for public application roles.

Repository state and deployment state are not the same claim. This page documents the current master branch and its deployment configuration. DNS, hosting availability or a pending deploy can still differ temporarily from the repository. None of that changes the clinical status: this remains a development prototype.

Verification represented by the repository

The final merged conversational-context phase reports 285 passing backend tests together with clean TypeScript and Vite builds. The repository also now contains CI jobs for backend tests, frontend compilation/build and applying, reapplying and verifying the database migrations against a disposable PostgreSQL instance shaped around the intended Supabase role model.

Those checks are engineering evidence, not clinical validation. They test software contracts and regressions; they do not establish sensitivity, specificity, calibration, outcome benefit or medical-device performance.

What is not released yet

A separate draft pull request introduces a new PsychDeep visual mark and reuses its wave geometry as the application icon and breathing pacer. Because that work is still a draft rather than part of master, it is deliberately not described here as a released feature.

Clinical limits

  • Not a validated medical device. The project has not undergone prospective clinical validation or regulatory conformity assessment.
  • Not a diagnostic system. Model outputs and deterministic scores do not establish psychiatric diagnoses or causal explanations.
  • Not an emergency service. Server-owned crisis messaging and escalation logic are safety features inside a prototype, not a substitute for emergency assessment or care.
  • Model output remains fallible. The analyser can miss a relevant marker or produce a false signal; model provenance and human correction exist because that failure mode is expected.
  • Thresholds are implementation choices. Traceability makes them visible; it does not make them clinically validated.
